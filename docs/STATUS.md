# BEAM Watch 開発記録

## 企画

- 目的: Gleam と BEAM の並行処理を学ぶため、複数 URL を同時に確認する死活監視 CLI を作る。
- 実行基盤: Erlang/OTP 上の BEAM。
- 入力: コマンドライン引数として 1 個以上の URL を渡す。
- 判定: HTTP 2xx/3xx は `OK`、4xx/5xx・接続失敗・URL 不正は `NG`。
- 信頼性: 1 URL ごとに最大 3 回試行し、各試行の HTTP タイムアウトは 5 秒とする。

## 設計

- メインプロセスが結果受信用の `Subject` を作る。
- URL ごとに BEAM の軽量プロセスを起動する。
- 各ワーカーは HTTP を確認し、型付きの結果メッセージをメインプロセスへ送る。
- メインプロセスは到着順に結果を表示する。したがって遅い URL が他の URL の表示を妨げない。
- OTP の HTTP クライアント内部の例外は最小の Erlang FFI で `Error(Nil)` に変換し、ワーカーが結果を返さず終了しないようにする。

## 実装

- 状態: 完了
- 実装内容: Gleam の `process.spawn_unlinked` と `Subject` を使い、URLごとに並行ワーカーを起動するCLIを実装した。
- 依存関係: `argv`、`gleam_erlang`、`gleam_httpc`、`gleam_http`、`gleam_stdlib`、テスト用の `gleeunit` を追加した。

## 評価

- 状態: 合格
- `gleam format --check`: 合格
- `gleam test`: 3件合格
- 実通信: `http://httpbin.org/status/200` は `OK (HTTP 200)`、`http://httpbin.org/status/404` は `NG (HTTP 404)`、`http://example.invalid` は `NG` を返すことを確認した。結果は入力順ではなく到着順に表示された。
- 補足: このサンドボックスのポータブルOTPはWindows証明書ストアを読み込めず、HTTPS開始時にOTP内部例外が起きた。この例外は `NG` として処理され、TLS証明書検証を無効化していない。

## GUI 版の計画

- 状態: 計画（未着手）
- 目的: CLI で確認した並行監視を、Web ブラウザから URL を登録して結果をリアルタイムで確認できる画面にする。
- 位置づけ: 学習用プロジェクト。動く最小構成を作るだけでなく、Gleam と BEAM の特徴的な機能（型、OTP、マルチターゲット、テスト手法）をできるだけ多く触ることを目的にする。
- 方針: 既存の CLI 監視ロジック（並行ワーカー・再試行・判定）を再利用し、Web サーバーと画面を足す。サーバー（Erlang ターゲット）・フロント（JavaScript ターゲット）・共通の型の 3 つに分けて、1 つの言語で両側を書く構成を学ぶ。

### 機能

- URL の登録・削除（画面からテキスト入力）
- 登録した全 URL を並行チェックし、結果を到着順に画面へ表示
- 各 URL の状態（OK / NG、HTTP ステータス、最終確認時刻）を一覧表示
- 一定間隔（既定 5 秒）で自動再チェック、手動の「今すぐチェック」ボタン
- 監視対象の追加・削除を反映した再チェック

### 構成

- サーバー: Wisp + Mist で HTTP サーバーを立てる。
- 監視コア: `src/beam_watch.gleam` の `check_with_retries`・`check_once`・`is_healthy_status` をそのまま再利用する。
- 状態保持: 監視対象 URL の一覧と直近の結果を、OTP の actor が保持する。supervisor 配下に置き、落ちても再起動される。
- 定期チェック: `send_after` によるサーバー側タイマー。
- 画面: Lustre で作る SPA。結果は、まずポーリングで取得する（WebSocket / SSE は後回し）。
- 型の共有: サーバーとフロントで使う型（監視対象、結果など）を `shared` に切り出す。

### 実装ステップ

1. 最小のサーバー: Wisp で Hello World、JSON を返すエンドポイントの起動確認。
2. OTP の actor: URL 一覧と結果を 1 つの actor に持たせ、メッセージで操作する。
3. supervisor と定期チェック: `send_after` で自動再チェックし、ワーカーが落ちても再起動されることを確認する。
4. 「全 URL を並行チェックし、結果を JSON で返す」エンドポイントと、監視対象の追加・削除エンドポイントの実装（既存監視ロジックを呼ぶ）。
5. Lustre のフロント: 一覧表示、追加・削除フォーム、ポーリング。
6. 共通の型: サーバーとフロントで使う型を `shared` に切り出す。
7. 永続化: `sqlight` で URL 一覧と履歴を保存する。
8. テスト: 既存の監視ロジックのテストを維持し、プロパティテスト（ステータスコード → OK/NG の判定）とスナップショットテストを追加する。
9. 発展: SSE または WebSocket でポーリングを置き換える（Mist が対応していると理解しているが、API は未確認）。

### 制約・留意点

- HTTPS 監視は TLS 証明書検証を維持する（無効化しない）。
- ポータブル OTP の証明書ストア問題（CLI 版で確認済）は GUI 版でも同じく `NG` として扱う。
- 結果の表示は到着順（入力順を保証しない）を維持する。
- 自動再チェックの間隔と再試行回数は CLI 版の既定値（5 秒タイムアウト・最大 3 回）を踏襲する。
- 実装は小さなステップに分けて進める。1 回の依頼で大量のファイル操作やコマンド実行をさせない（ローカル LLM のコンテキスト溢れ対策）。
