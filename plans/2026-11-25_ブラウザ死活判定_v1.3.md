# 計画書: ブラウザで開いた結果を死活にする(v1.3)

v1.2（`plans/2026-11-25_ブラウザ死活判定_v1.2.md`）に、次の1点を足す。ここに書いていないことは v1.2 のとおり。

## 追加の理由（2026-11-25 に確認した事実）

AI195417 から Vercel と camp のページが出ないのは、社内の Web フィルター「TS セキュリティ共通基盤サービス」が止めているからだった。

- サーバーから平文 HTTP で開くと、503 のブロック画面が返る。ブロック理由は `web-hosting`、利用者の欄は `global\aadmz100db110`。
- 確かめた URL: `fieldstyle-nav.vercel.app`、`shadowing-lab-eight.vercel.app`、`udon-db.vercel.app`、`camp.jugo-shoten.com`。4件とも同じブロック画面だった。
- HTTPS では、ブロック画面の代わりに接続を切る。Edge は `ERR_CONNECTION_RESET`、curl は終了コード 35 になる。そのため、今の NG の理由は「ページを取得できない」としか出ない。
- この要求は私のアカウント（0120025-Z100）で出したが、フィルター側は AAdmZ100DB110 と表示した。フィルターは、送信元 IP にログオン中のユーザーを結び付けて判定している。BrowserCheck をどのアカウントで動かしても、結果は変わらない。
- 同じネットワークのこの PC（172.26.211.112）からは、4件とも開ける（200 または 302）。

## 変えるもの（v1.2 への追加）

- `deploy/server/BrowserCheck.ps1`: ページが出なかったときに、同じホストへ平文 HTTP（80番）で1回だけ問い合わせる。応答が「TS セキュリティ共通基盤サービス」のブロック画面なら、NG の理由を `社内フィルターでブロック (web-hosting)` とする。括弧の中は、ブロック画面のブロック理由をそのまま入れる。ブロック画面でなければ、v1.2 のとおり Edge のエラーコードを理由にする。
- OK の条件は変えない。ブロックされたサイトは NG のまま。

## 検証方法（v1.2 への追加）

- 配備後の `/api/results` で、ブロックされている外部サイトの理由が `社内フィルターでブロック (web-hosting)` になっている。

## 変えないもの・やらないこと

- Web フィルターの例外申請はしない。システム管理者への相談は、必要ならユーザーが行う。
- 監視対象から外部サイトは外さない（v1.2 のとおり 4件残す）。外すかどうかはユーザーが決める。
